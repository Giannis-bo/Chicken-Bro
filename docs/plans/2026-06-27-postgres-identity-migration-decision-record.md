# PostgreSQL 迁移与产品架构决策纪要

日期：2026-06-27

状态：已确认，待实施

范围：主数据库迁移、强身份、用户资产、SimC 任务、Chickenbro 多会话、通用知识库、资讯、analytics、ops。

> 当前代码和线上运行时仍以 SQLite 为准。本纪要记录下一阶段目标态和迁移边界，不能被解读为已完成 PG 切换。

## 1. 背景与目标

SQLite 已经支撑了资讯、账号模板、WebSim/Season Data Cache、SimC 任务、Chickenbro 骨架和 analytics 的早期阶段，但后续会遇到写锁、并发任务、数据域膨胀、用户资产治理、检索和运维可观测限制。下一阶段目标是把主库切换到 PostgreSQL，并把用户身份作为所有个人数据的统一 owner 边界。

这一阶段同时承接产品方向升级：

- 所有天赋、装备、构筑档案、SimC 历史、Chickenbro 会话和个人上下文都归属到具体用户。
- 公共知识、可重建缓存、个人上下文和运维数据在数据库层分域。
- Chickenbro 从单次问答走向多会话的证据教练。
- 资讯和公共知识库要有通用存储与可信状态。
- 监控和统计同时覆盖产品行为闭环与底线运维健康。

## 2. 大版本范围

本阶段作为同一个大版本治理，实施可以分批，但最终验收应放在同一条主线下：

- SQLite 主库切换到 PostgreSQL。
- 强登录和统一用户身份。
- 后端构筑档案聚合层。
- SimC 任务用户化、快照化和可追溯。
- Chickenbro 多会话和个人上下文。
- Chickenbro v1 公共知识库检索。
- 数据可信状态产品化。
- 基础监控、analytics 和轻量 ops console。

## 3. PostgreSQL 目标态

生产环境使用服务器本地 PostgreSQL，不在第一阶段引入外部云数据库。

开发、测试和生产使用同一 PG 实例下的不同 database：

- `wow_prod`
- `wow_dev`
- `wow_test`

第一阶段采用单实例、多 database、多 schema。业务 schema 划分如下：

- `identity`：用户、第三方身份、token、权限基础。
- `app`：用户资产、构筑档案、模板、SimC 任务、Chickenbro 会话。
- `content`：资讯、来源、原文、证据、发布状态。
- `cache`：WebSim、Season Data Cache、装备、天赋、外部源索引。
- `knowledge`：Chickenbro 公共知识库、个人上下文摘要、检索索引。
- `analytics`：事件、日聚合、漏斗和留存指标。
- `ops`：迁移记录、任务队列状态、同步运行、审计日志、健康快照。

迁移机制先使用轻量 SQL migration，不引入 Alembic。需要至少区分这些数据库角色：

- `migrator`：只用于迁移。
- `app_rw`：应用读写。
- `readonly`：排查、报表和只读查询。
- `backup`：备份任务。

## 4. 迁移边界

需要迁移：

- 正式用户数据。
- 用户保存的天赋模板、装备模板和后续构筑档案。
- 已归属用户的 SimC 任务和任务快照。
- Chickenbro 已归属用户的会话、消息、任务和画像摘要。
- 资讯、来源、原文、证据和发布状态。
- WebSim/Season Data Cache、装备、天赋、社区模板和 health 所需缓存。

不迁移：

- guest 用户、guest 任务、guest 会话。
- 旧 auth token。
- 无法归属用户的临时调试数据。

旧 token 不迁移，切换后要求重新登录。PG 切换前必须备份 SQLite；PG 上线后建立每日 `pg_dump`，保留 14 到 30 天。

## 5. 身份与个人资产

用户体系以独立 `users` 为根，微信身份作为 `user_identities` 的一种 provider。后续即使接入其他登录方式，也不应把业务表直接绑死到微信 openid。

所有写入型个人资产必须有 `user_id`：

- 天赋模板。
- 装备模板。
- 构筑档案。
- SimC 任务。
- Chickenbro 会话和消息。
- Chickenbro 个人上下文。
- 收藏、订阅、反馈等后续个人能力。

登录策略采用“行动前登录”：浏览可以保持游客态，保存、提交任务、创建 Chickenbro 会话、写个人上下文、收藏和订阅必须登录。

由于国服没有稳定可用的 Armory API，本阶段不做“真实游戏角色档案”。产品语义使用“构筑档案”：它代表用户保存或提交模拟时形成的结构化配置，不声明等同于游戏内真实角色。

构筑档案第一阶段只做后端聚合层，不新增独立前端页面。入口仍保持：

- “我的”：天赋模板、装备模板和后续构筑档案汇总。
- “任务列表”：SimC 历史。
- Chickenbro：对话和复盘会话。

构筑档案只在保存模板或提交最终 SimC 时写入。浏览、预览、确认、临时草稿不写长期资产。后端同时保留当前状态和历史快照，并按 `user_id + name + config_hash` 去重。

## 6. SimC 任务模型

SimC 任务仍是玩家可见的模拟历史，不单独做“构筑工作台”页面。

每个 SimC 任务必须保存提交时的完整快照，包括：

- 用户身份。
- 职业、专精、种族、英雄天赋。
- 场景。
- 天赋模板快照。
- 装备模板快照。
- SimC 输入摘要和执行所需内部字段。
- 结果、失败原因、完成时间和任务列表 summary。

任务详情必须基于任务快照展示，不受之后用户修改模板或构筑档案影响。任务列表只读取紧凑 summary，不应反解析完整 `request_json` / `analysis_json`，也不应触发装备属性计算。

当前执行模型本阶段先沿用现状：Web 后端接收请求、写入任务、启动或推进 runner，并通过任务表更新 `queued -> running -> completed/failed`。PG 表结构需要预留 worker-ready 字段，例如 heartbeat、attempt、locked_by、queued_at、started_at、finished_at、cancel_requested、last_error。

独立 worker 不进入本轮切换范围，但作为后续优先级第一的待规划项。

## 7. 独立 worker 的后续含义

现状表示任务执行仍依附 Web 后端进程和当前 runner 机制，任务状态以数据库行为主，但没有独立 durable worker 进程承担完整队列生命周期。

升级独立 worker 表示：

- Web 后端只负责校验、入队、查询和取消请求。
- 独立 worker 进程轮询或订阅任务队列。
- worker 负责并发控制、retry、cancel、timeout、crash recovery、heartbeat、日志归档和失败归因。
- SimC 与 Chickenbro 后续可以使用同一套任务执行治理。

本轮只在 PG schema 中为这些能力留字段，不切换执行架构。

## 8. Chickenbro 定位

Chickenbro 长期定位是证据教练，不是泛聊天。核心用户是高端复盘玩家，第一重点是 DPS/HPS 表现分析。

首版输出应是优先级行动清单：

- 你最该先改什么。
- 为什么这么判断。
- 证据来自哪里。
- 缺哪些证据时不能下结论。
- 下一次如何验证行动是否有效。

如果证据不足，只输出证据收集 checklist，不伪造个人诊断。行动清单做轻量 tracking，不做完整 todo 系统。

## 9. Chickenbro 多会话

Chickenbro 必须支持多个会话。一个会话代表一个复盘主题或上下文，例如：

- 20 层通天峰。
- M 鲁拉开荒。
- 元素萨 AOE 输出复盘。

玩家可以今天创建通天峰会话，明天新建 M 鲁拉会话，后天再回到通天峰继续聊。不同会话默认互不污染。

每个会话至少保存：

- `user_id`
- 标题
- 场景
- 职业、专精、英雄天赋
- 关联构筑档案
- 关联 SimC 任务
- 关联 WCL 输入
- 消息
- 行动清单
- 会话摘要
- 更新时间

会话列表按最近更新时间排序，支持恢复旧会话。

## 10. 上下文与知识边界

Chickenbro 使用三层上下文：

1. 会话上下文：当前复盘主题里的 SimC、WCL、构筑、行动清单和会话摘要。
2. 用户长期上下文：用户常玩的职业/专精/场景、反复出现的问题、已验证过的行动结果。
3. 公共知识库：runbook、roadmap、WebSim readiness、公共机制、社区趋势、Wowhead/Raider.IO/Archon.gg 等可引用资料。

回答优先级为：会话上下文 > 用户长期上下文 > 公共知识库。

跨会话默认不引用。只有当用户明确提到另一个会话，或某个结论已经被沉淀为用户长期摘要时，才可以跨会话使用。

个人会话和个人上下文绝不自动进入公共知识库。玩家授权分享到公共知识库是后续待规划能力。

权限边界：

- 公共知识：所有用户可读。
- 用户长期上下文：仅 owner 可读。
- 会话上下文：仅 owner 且当前会话可读。

## 11. 公共知识库与 Embedding Provider

本阶段没有可用的 Embedding Provider。Chickenbro v1 不以 embedding 作为上线前置条件。

第一阶段检索采用：

- PostgreSQL full-text search。
- 结构化标签。
- 来源、版本、职业、专精、场景和可信状态过滤。

PG schema 可以低成本预留 embedding 或 pgvector 字段，但默认禁用，不写入运行路径。

Embedding Provider 或离线向量生成记录为待规划项。未来如果接入，需要明确：

- provider 来源。
- 成本和调用频率。
- 离线生成还是在线生成。
- 向量重建策略。
- stale/blocked 状态。
- 个人数据是否允许进入向量索引。

## 12. 外部来源原则

外部来源优先选择可授权、可审计、可引用的接口或公开引用方式。第一阶段不做不可控全文抓取。

证据分层：

- 个人 SimC、WCL、构筑快照：个人诊断的主证据。
- Wowhead、Raider.IO、Archon.gg 等：社区参考、机制说明或趋势背景。
- 本地推理：只能作为解释层，不替代证据。

没有个人验证时，只能给趋势建议或假设，不能说“这就是你的最优答案”。公共知识过期时降级为背景材料，不进入行动清单支撑链。

## 13. 数据可信状态产品化

面向玩家统一使用中文语义状态：

- 已验证
- 证据不足
- 暂不能执行
- 可能过期
- 仅供参考

默认展示采用“简洁 + 可展开”：

- 默认显示可信状态和关键原因。
- 展开后显示来源、时间、适用范围、blocker 和验证方式。

当系统拒绝保存、拒绝模拟、拒绝复盘或拒绝强结论时，必须显示：

- 简短原因。
- 下一条可补证据路径。

Chickenbro 的每个行动建议都应绑定 evidence state 和来源摘要。

## 14. 资讯存储

资讯链路按 `source -> raw -> evidence -> article` 分层。

资讯分类采用固定 category + 自由 tag：

- category 用于导航和筛选。
- tag 用于细粒度主题、职业、赛季、活动、版本等。

可信来源可以自动发布，但必须支持下架、标记过期和标记需复核。第一阶段不做完整 CMS。CMS / 内容编辑后台记录为待规划项。

## 15. Analytics

登录前事件只记录匿名 session/client hash。登录后的事件写入 `user_id`。不回填登录前匿名事件到用户身份。

事件保留策略：

- raw events 保留 180 天。
- daily rollup 长期保留。

产品判断优先看用户行为和复盘闭环：

- 保存构筑。
- 提交 SimC。
- 查看任务。
- 创建 Chickenbro 会话。
- 返回旧会话。
- 行动清单是否被后续验证。
- 哪些入口带来留存。
- 哪些 blocker 造成中断。

## 16. Ops 与管理能力

第一阶段做轻量 ops console，不做完整运营后台。

需要覆盖：

- 系统健康。
- 同步状态。
- 任务状态。
- 数据可信状态。
- analytics 汇总。
- 公共内容状态治理。
- 用户问题的摘要级排查。

用户问题排查默认只看摘要，不默认暴露完整聊天、完整 SimC profile 或 raw request。

公共内容治理第一阶段只支持：

- 下架。
- 标记过期。
- 标记需要复核。
- 记录原因。

不做富文本编辑。

权限第一阶段使用单一 admin token。admin / moderator 角色体系是后续待规划能力。

所有 admin 行为必须写 `ops` 审计日志。

## 17. 数据增长策略

数据库数据按三类治理：

1. 长期用户资产：构筑档案、模板、SimC 历史、Chickenbro 会话、行动摘要、用户长期上下文。长期保留，支持用户删除和匿名化。
2. 可重建公共证据缓存：WebSim、装备、天赋、社区样本、属性权重、外部来源索引。必须可追踪来源、可信状态和重建方式。旧版本保留摘要或关键证据，明细可归档或重建。
3. 短期运维排查数据：job 中间状态、同步 run、失败日志、agent payload、heartbeat。短期保留，定期清理或压缩。

## 18. 监控指标

产品层指标：

- 用户保存构筑。
- 用户提交 SimC。
- 用户查看任务详情。
- 用户创建多个 Chickenbro 会话。
- 用户回到旧会话继续复盘。
- Chickenbro 行动清单产生后是否有后续验证。
- 哪些入口驱动留存。
- 哪些 evidence/blocker 导致中断。

底线运维指标：

- DB 体积。
- 慢查询。
- 任务失败率。
- 同步健康。
- job backlog。
- PG 连接数。
- 存储增长。
- 关键 API 错误率。

产品判断优先看用户行为和复盘闭环，但底线运维指标必须存在。

## 19. 本轮明确不做

- guest 数据迁移。
- 旧 token 迁移。
- 新“构筑工作台”前端页面。
- 完整 CMS。
- Embedding Provider。
- 离线向量生成。
- 独立 worker。
- 玩家分享内容进入公共知识库。
- 数据导出。
- admin / moderator 角色体系。
- 复杂复盘工作台。

## 20. 后续待规划

优先级第一：

- 独立 worker：将 SimC / Chickenbro 执行从 Web 后端拆出，支持 retry、cancel、recovery、heartbeat、并发控制和队列监控。

其他待规划：

- Embedding Provider 或离线向量生成。
- 玩家授权分享个人经验到公共知识库。
- CMS / 内容编辑后台。
- admin / moderator 角色体系。
- 复杂复盘工作台。
- 公共知识库玩家贡献审核流。
