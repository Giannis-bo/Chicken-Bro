## 已确认方向

用户认可本地定期扫描「未解决」反馈、对照验证、根因聚类、通用修复与回归的方向，并补充：定期扫描后汇总报告，由用户人工确认。扫描器、问题组版本绑定决策、重复回放证据门禁与有条件发布执行器已实现；2026-09-10 零点 heartbeat 已实际唤醒并完成增量扫描。当前 G6 两条获准反馈的 V9 正式验收因超时失败，已自动回滚并通过恢复业务验证；V10 重新进行完整 HTTP 对照及发布验收；G7 新反馈待决策，不进入本批。

## 工作流

1. 增量读取 `resolved=false`，使用反馈时间与 run ID 游标、去重、运行锁、预算和断点恢复。原始反馈不被诊断结果覆盖。
2. 构建问题包：截至原提问的上下文、原回答、实际模型输入、运行与配置身份、脱敏工具调用证据、来源时间及相关 SimC 快照。缺失的历史证据标记缺失；不以当前查询结果冒充历史事实。不保存模型内部思维链或凭据。
3. 在求解前定义可核验的验收条件。对照生产条件复现、本地诊断求解与修复后的生产等价验证；记录本地新增的工具、权限、数据和时间预算，避免把资源差异直接归因为代码缺陷。
4. 按失败机制归组，给出证据、假设、影响范围、建议及成本；按批次提交人工决策报告。
5. 用户按问题组决定修复、继续调查、暂缓或标记未发现可验证缺陷。批准修复后进入隔离开发与回归；发布继续遵循现有 Candidate 与验收边界。
6. 回归覆盖原问题、同机制变体、未用于调试的留出样本、正常回答和权限边界。报告修复前后结果与耗时成本，不以原题单次成功证明泛化。

## 通用修复与泛化验收（必须满足）

- 修复必须针对有证据支持、可解释且可复用的失败机制，明确适用范围与不适用边界；原始 badcase 是发现和复现缺陷的证据，不是生产逻辑的匹配条件。不得以 case by case 补丁代替机制修复。
- 禁止为通过案例，在代码、提示词、配置或数据映射中按特定问题文本、用户/角色名、会话/run ID、报告 ID 或原题答案增加特判、硬编码回答或白名单。测试夹具可以保留原始案例；必要的领域规则必须有独立于该案例的合同或可信来源依据，并验证同类输入及边界，不能以“领域规则”为由包装案例特判。
- 在调试前固定验收条件和样本划分。修复后必须分别验证原问题、同机制变体、未参与调试或方案选择的独立留出样本、正常路径及权限边界；变体应改变与根因无关的名称、措辞、标识或上下文，不能只重复原题。留出样本一旦用于调整修复，就转为调试样本，并补充新的独立留出样本。
- 验证报告必须说明根因证据、机制改动、适用边界、反特判审查结论，以及各类样本在相同条件下的修复前后结果、重复验证通过率（涉及模型随机性时）、耗时与成本；绑定实际源码、提示词/配置和运行身份。不得只展示成功样本，不以原题单次成功或测试总数证明泛化。
- 发现案例特判、缺少同机制变体或独立留出样本证据、未达到预先定义的验收条件，或出现正常路径/权限边界回归时，不得标记修复完成，也不得进入自动发布批次。证据不足记为“泛化未验证”，继续调查或提交人工决策；不能降级标准后自动放行。

以上是工作流和调度提示词必须遵循的拒绝条件。本轮已实现逐组结构化证据门禁，检查原题、变体、独立留出、正常与权限样本、重复实验独立身份及成本；执行链路仍须以真实发布验收记录确认，不能将代码实现等同线上闭环。

## 验证范围与停止条件（2026-09-10 补充）

- 泛化通用工具方案的验证必须适可而止：围绕有证据支持的失败机制和已声明适用范围，不无限扩展场景，不做无尽穷举。
- 调试前固定最小充分的代表样本、重复次数、总调用/耗时预算和停止条件。在现有门禁最低要求内覆盖原问题、同机制变体、独立留出、正常路径与权限边界；不枚举所有名称、职业、措辞或参数组合。
- 预定验收通过且无阻断回归后立即收敛，进入已授权的后续流程；不能仅因想到更多场景就追加验证。
- 仅新失败证据、实际代码/配置变动或明确合同风险可触发受影响范围的补测。身份、条件和有效期仍符合现有门禁的已通过证据应复用，不无故整套重跑；组合回归只覆盖实际受影响的交互。
- 留出样本被用于调试时仍须更换，但更换与复测计入原总预算，不自动扩容。预算耗尽或连续验证不再提供新信息时停止，保留失败与未覆盖范围，标记未验证/暂缓并报告具体缺口；不得降低标准放行，也不得跨自动化窗口重置预算后盲重试。
- 无关新场景另列后续事项，不并入当前修复；扩大范围或预算应有具体新证据及相应授权，不能以“证明通用性”为由持续追加。

## 判定原则

- 本地可解、生产条件失败：可修复缺陷候选，需要通过控制变量验证根因。
- 偶发成功：记录重复验证通过率，调查稳定性。
- 仅增加模型能力、预算或权限后可解：能力或资源差距，交用户决策。
- 两边均未解决：暂未验证可解；不推断用户乱点。
- 原答案满足验收条件：未发现可验证缺陷；保留用户反馈与判定分歧。
- 事实与执行状态优先程序/来源验证；开放式答案独立评审，隐藏来源；争议交人工。

## 人工报告与决策合同

每批报告包含：扫描时间范围、游标与覆盖数量、去重后数量、已验证/证据不足/未完成数量、预算消耗；没有新问题时只给简短周期摘要。

每个问题组包含：组 ID、受影响反馈数及去重会话数、代表问题、云端表现、本地验证证据、根因假设与置信依据、预期通用修复、回归范围、成本及需要用户决定的事项。不能把聚类或模型评价直接当成已证实根因。

用户可按组回复“修复 G1/G2，G3 继续调查，G4 暂缓”，不要求逐条审阅聊天。对不确定问题可展开脱敏原始证据。决策绑定报告版本与问题组；后续新增证据或扩大范围必须重新提出，不把未回复当批准。

修复后另附满足“通用修复与泛化验收”的逐组验证报告，区分本地验证、Candidate、正式发布和用户验收。生产发布采用下述每日条件发布策略；不修改原用户会话或原始反馈。
