## 工作流

1. 增量读取 `resolved=false`，使用反馈时间与 run ID 游标、去重、运行锁、预算和断点恢复。原始反馈不被诊断结果覆盖。
2. 构建问题包：截至原提问的上下文、原回答、实际模型输入、运行与配置身份、脱敏工具调用证据、来源时间及相关 SimC 快照。缺失的历史证据标记缺失；不以当前查询结果冒充历史事实。不保存模型内部思维链或凭据。
3. 在求解前定义可核验的验收条件。对照生产条件复现、本地诊断求解与修复后的生产等价验证；记录本地新增的工具、权限、数据和时间预算，避免把资源差异直接归因为代码缺陷。
4. 按失败机制归组，给出证据、假设、影响范围、建议及成本；按批次提交人工决策报告。
5. 用户按问题组决定修复、继续调查、暂缓或标记未发现可验证缺陷。批准修复后进入隔离开发与回归；发布继续遵循现有 Candidate 与验收边界。
6. 回归覆盖原问题、同机制变体、未用于调试的留出样本、正常回答和权限边界。报告修复前后结果与耗时成本，不以原题单次成功证明泛化。

## 判定原则

- 本地可解、生产条件失败：可修复缺陷候选，需要通过控制变量验证根因。
- 偶发成功：记录重复验证通过率，调查稳定性。
- 仅增加模型能力、预算或权限后可解：能力或资源差距，交用户决策。
- 两边均未解决：暂未验证可解；不推断用户乱点。
- 原答案满足验收条件：未发现可验证缺陷；保留用户反馈与判定分歧。
- 事实与执行状态优先程序/来源验证；开放式答案独立评审，隐藏来源；争议交人工。

## 人工报告与决策合同

每批报告包含：扫描时间范围、游标与覆盖数量、去重后数量、已验证/证据不足/未完成数量、预算消耗；没有新问题时只给简短周期摘要。

每个问题组包含：组 ID、受影响反馈数及去重会话数、代表问题、云端表现、本地验证证据、根因假设与置信依据、预期通用修复、回归范围、成本及需要用户决定的事项。不能把聚类或模型评价直接当成已证实根因。

用户可按组回复“修复 G1/G2，G3 继续调查，G4 暂缓”，不要求逐条审阅聊天。对不确定问题可展开脱敏原始证据。决策绑定报告版本与问题组；后续新增证据或扩大范围必须重新提出，不把未回复当批准。

修复后另附验证报告，区分本地验证、Candidate、正式发布和用户验收。生产发布采用下述每日条件发布策略；不修改原用户会话或原始反馈。
