# Builds Home 职业命令卡组设计

状态：`用户已确认 · current-ui active design · 紧凑入口与最近任务修订`

确认日期：`2026-07-21`

关联里程碑：`taro_target_first_14_route_rebuild`

关联路由：`builds_home`（`apps/mini-taro/src/pages/builds/builds.tsx`）

## 1. 用户目标与当前问题

玩家进入“专精”一级入口时，只需要快速完成四件事：进入天赋模拟、进入装备模拟、进入 SimC 模拟、查看任务。当前页面同时展示大专精介绍、2×2 导航、工作台横幅、重复功能列表和流程时间线，同一组能力被重复表达，首屏层级和操作语义都过重。

目标体验是一个清晰的职业工具启动页：玩家只选择一次职业，随后从四个平级入口进入对应工具，并在同一首屏继续查看最近三次 SimC 任务。首页不要求玩家提前理解或选择天赋专精、英雄天赋、模板准备状态或模拟流程。

## 2. 已确认的产品决策

1. 采用 A 方案“紧凑命令卡组”：四张纵向排列的紧凑横向卡片，固定顺序为天赋、装备、SimC、任务。
2. 四个功能彼此独立。固定顺序只服务扫描效率，不表达步骤或完成进度。
3. 首页公共选择器只选择职业，例如“法师”，不选择“冰霜法师”等专精，也不选择英雄天赋。
4. 天赋、装备、SimC 继承当前职业；任务完全独立，不接收职业上下文。
5. SimC 首页入口不展示天赋模板、装备模板或准备状态。模板依赖只在 SimC 页面内部处理。
6. 四张卡本身不展示编号、进度、校验状态、动态数量、最近记录或快捷操作；任务事实进入独立的最近模拟区域。
7. 首页首屏必须完整展示职业选择器、四张卡和最近三次 SimC 任务，不产生业务内容纵向滚动。
8. 命令卡组与最近模拟区域共同铺满正文可用高度，从 header 下沿延伸到 `ProductTabBar` 上沿，不把缩小入口释放出的空间留成无意义空白。

## 3. 范围

### 3.1 本次包含

- 重构 `builds_home` 的信息架构和视觉 composition。
- 将首页选择语义从“具体专精”收敛为“职业”。
- 提供职业选择底部面板。
- 建立当前职业和每职业最近专精的轻量共享偏好。
- 让天赋、装备、SimC 启动时获得确定的专精上下文。
- 复用当前 owner-scoped 任务列表，展示按更新时间倒序排列的最近三次 SimC 任务。
- 让最近任务直接进入现有任务详情，并为 loading、empty 和 error 保留稳定区域。
- 更新 `builds_home` canonical target、route contract、核心交互合同和对应验证。

### 3.2 本次不包含

- 重做天赋模拟、装备模拟、SimC 或任务页面的主体交互。
- 在首页创建模板、提交模拟或展开完整任务报告。
- 改变后端 API、canonical 数据事实、SimC 执行语义或任务 owner。
- 将四个入口改造成线性工作流。
- 把可视化概念稿当作 canonical target、目标几何或微信验收证据。

## 4. 页面结构

### 4.1 顶部区域

- 保留一级标题“职业专精”。
- 标题右侧放置紧凑职业胶囊，内容为职业图标、职业名和展开箭头，例如“法师 ▾”。
- 不展示专精名称、英雄天赋、来源、缓存、校验或可用状态。

### 4.2 命令卡组

主体上半区包含四张平级紧凑卡片：

| 固定顺序 | 标题 | 固定说明 | 启动行为 |
| --- | --- | --- | --- |
| 1 | 天赋模拟 | 设计、导入与保存天赋模板 | 解析当前职业的启动专精并进入天赋模拟 |
| 2 | 装备模拟 | 搭配装备与增强方案 | 解析当前职业的启动专精并进入装备模拟 |
| 3 | SimC 模拟 | 组合模板并发起模拟 | 解析当前职业的启动专精并进入 SimC |
| 4 | 任务查看 | 查看模拟任务与结果 | 不携带职业或专精参数，直接进入任务列表 |

每张卡仅包含缩小后的功能图标、标题、单行固定说明和进入箭头。整张卡都是点击区域，不展开、不嵌套第二操作，也不在卡片内部显示动态状态。四张卡保持完整可点击高度，但明显降低装饰框、徽记、内边距和卡间距占用。

### 4.3 最近模拟

主体下半区固定展示“最近模拟”区域：

- 数据范围是当前账号或游客 owner 下的全部职业，不随顶部职业选择器过滤。
- 只接收真实 `wowApi.simulator.tasks()` 返回且 `mode === 'simcraft_template'` 的当前 SimC 提交任务，按 `updatedAt`、缺失时按 `createdAt` 倒序取前三条。
- 每行只显示职业/专精与场景、更新时间和真实状态；缺少字段时使用不推断事实的中性文案。
- 点击有效任务直接进入现有任务详情路由；完整任务列表仍由第四张“任务查看”卡负责，因此区域标题不再重复提供“查看全部”。
- 三条任务行等高，占据一个稳定区域；不足三条时由真实 empty 表达填充结构，不伪造任务。

### 4.4 满屏布局

- 页面正文使用上下两段式布局：紧凑命令卡组在上，最近模拟在下。
- 两区在标准目标视口按固定设计比例共同填满 shell 正文可用高度；底部边界对齐 `ProductTabBar` 上沿，不留下大块空白。
- 小屏首先压缩卡间距、区域间距和说明文字空间，再缩小非关键装饰；不得通过新增正文滚动、裁掉任务行或遮挡 TabBar 解决高度不足。
- 大屏通过两区内部的行高与间距在合同允许范围内弹性分配，不把全部内容堆在顶部。

### 4.5 视觉语言

- 延续现有暗色石材、黄铜边框、圆形职业/工具徽记和克制金色高光。
- 通过图标、卡片边界和字级维持游戏感，避免依赖复杂装饰或高密度文案。
- 点击反馈只做轻微压暗和黄铜边框提亮，不引入位移动画、展开动画或连续闪烁。
- 四张卡与三条任务行组成清晰的 `4 + 3` 纵向节奏；工具入口更强、最近任务更轻，不争夺一级入口层级。
- 两个区域共同在 shell 正文可用高度内弹性分配，底部 `ProductTabBar` 继续由共享 owner 管理。

## 5. 职业选择面板

点击职业胶囊后，从底部打开“选择职业”面板：

- 以三列图标网格展示 canonical payload 中的 13 个职业。
- 每项只显示职业图标和职业名称；不进入第二层，不列出专精或英雄天赋。
- 当前职业使用唯一金色选中态。
- 点击可用职业后立即保存选择、关闭面板并更新胶囊。
- 关闭或取消不改变当前职业。
- 没有任何有效专精映射的职业保持可见但置灰，不能建立虚假模拟上下文。

面板本身可以在极小视口内使用独立内容滚动兜底，但不得推动首页正文或制造首页滚动；标准目标视口应一次展示全部职业。

## 6. 上下文与数据流

### 6.1 共享偏好

前端维护两个轻量偏好：

- `selectedClassKey`：首页当前职业。
- `lastSpecByClass`：职业到最近有效专精 ID 的映射。

它们只决定工具的默认启动上下文，不是构筑事实、模板 owner 或模拟输入本体。职业/专精映射的有效性始终由当前 canonical builds-home payload 校验。

### 6.2 启动专精解析

天赋、装备或 SimC 被点击时，按以下确定顺序解析具体专精：

1. 找到当前职业在 canonical payload 中的全部有效专精。
2. 若 `lastSpecByClass[currentClass]` 仍在有效集合中，使用该专精。
3. 否则使用该职业在 canonical payload 中的首个有效专精，并覆盖失效偏好。
4. 若当前职业已失效，优先改用包含现有全局默认专精的职业；仍不可用时选择首个拥有有效专精的职业。
5. 若没有任何有效职业/专精映射，进入 route-level blocked 状态，不生成占位专精。

首页解析出具体专精后，继续通过现有 `spec` 路由参数进入三个工具，避免给工具页面引入第二套并行启动合同。

### 6.3 工具内更新

天赋、装备或 SimC 内部切换专精时，更新该职业的 `lastSpecByClass`。这让三个独立工具下次进入时共享用户最近选择，但不共享草稿、模板内容、校验状态或提交状态。

英雄天赋仍由天赋模拟内部管理，不进入首页共享偏好。

### 6.4 最近任务读取

首页独立调用现有 `wowApi.simulator.tasks()`：

1. 保持与任务列表页一致的当前账号/游客 owner 解析和 typed transport 校验。
2. 过滤为 `mode === 'simcraft_template'` 的当前 SimC 提交任务，使用现有任务状态与时间归一化逻辑；其他历史分析模式不混入首页预览。
3. 按最新时间排序并截取前三条；不按当前职业过滤，不推断缺失的职业、专精、场景、DPS 或完成结果。
4. 任务预览请求失败只影响最近模拟区域，不阻断职业选择和四个工具入口。
5. 从任务详情返回首页时重新读取任务，以反映真实状态变化。

## 7. 组件边界

建议保持以下职责分离：

- `BuildsHomePage`：组合 shell、标题、职业选择器和四入口卡组，负责导航。
- `BuildClassSelector`：显示当前职业胶囊，管理底部面板的打开、关闭和选择事件。
- `BuildToolCommandDeck`：以静态配置渲染四张平级卡，不读取模板或任务状态。
- `BuildRecentSimcTasks`：消费已归一化的三条任务预览，拥有行状态、空态和任务详情点击，不读取职业偏好。
- shared build context resolver：校验并解析 `selectedClassKey`、`lastSpecByClass` 和启动专精。
- shared task-list model：继续拥有任务排序、状态和时间归一化；首页只增加受限的 preview adapter，不复制任务事实。
- simulator pages：继续拥有各自的专精/英雄天赋选择、模板、草稿、校验和提交状态。

当前首页中的大专精概览、证据导航、工作台横幅、重复列表和流程时间线从 `builds_home` composition 移除。只有确认无其他调用方后，才删除对应共享组件或模型代码。

## 8. 页面状态与异常处理

- 正常 ready 状态不显示任何状态标签。
- 职业目录初次加载和失败继续使用 `RouteStage` 的共享 loading/error/blocked 表达，不把异常状态塞进四张卡。
- 最近任务独立加载：首次请求显示三行等高骨架；owner 无任务时显示一个占满最近区域的克制空态；请求失败时显示区域级错误和重试，不阻断四个入口。
- 职业切换过程中不重载整个页面；只更新本地选择和后续启动上下文。
- 导航失败时留在首页并显示简短 toast，不改变职业偏好。
- SimC 缺少天赋或装备模板时，仍然允许进入，由 SimC 页面说明缺失项并提供处理路径。
- 存储中的职业或专精失效时按第 6.2 节确定性重新选择，不向用户展示陈旧名称。

## 9. 可见验收标准

### 9.1 正常首页

- 首屏同时看到标题、当前职业、天赋/装备/SimC/任务四张紧凑卡和最近三次 SimC 任务区域。
- 页面没有业务内容纵向滚动，底部导航不遮挡最近任务；`4 + 3` 结构从 header 下沿铺满到 TabBar 上沿，不出现大块无意义空白。
- 不出现专精介绍、工作台横幅、重复入口、流程时间线、编号或状态标签。
- 四张卡视觉平级，SimC 不因模板依赖获得额外强调或状态芯片。
- 最近任务视觉层级低于四个主入口，每条只呈现真实状态、时间和必要上下文。

### 9.2 职业选择

- 点击职业胶囊打开底部面板。
- 面板只展示职业，不展示专精和英雄天赋。
- 选择职业后胶囊立即更新；关闭面板后首页四卡结构不变。
- 再次进入页面可恢复上次职业。

### 9.3 工具启动

- 天赋、装备、SimC 都进入当前职业下的最近有效专精；首次使用采用该职业首个有效专精。
- 在任一工具切换专精后，从首页进入另一个工具时继承该职业最近专精。
- 任务入口不携带职业/专精上下文。
- SimC 即使缺少模板也能进入，缺失提示只出现在 SimC 内部。

### 9.4 最近任务

- 最近三条按真实更新时间倒序展示，跨职业且不随职业选择器变化。
- 排队、运行中、已完成、失败和未知状态使用现有真实状态映射，不把未知或失败伪装为完成。
- 点击有效任务进入对应详情；无任务、加载和失败时结构高度稳定，上方四入口始终可用。

## 10. 验证设计

### 10.1 自动验证

- resolver 单元测试：有效记忆、失效记忆、首次默认、职业失效、全量缺失和跨职业隔离。
- 首页 model/page contract：恰好四个入口、固定顺序、卡片无动态状态字段、任务入口无参数、三个模拟入口携带解析后的 `spec`。
- 最近任务 preview model：只接收 `mode === 'simcraft_template'` 的当前 SimC 提交任务、按时间倒序取三条、跨职业、缺失字段不推断，并覆盖少于三条、无任务和非法时间。
- 交互测试：职业面板打开/取消/选择、职业持久化、工具内专精回写和导航失败不污染选择。
- 最近任务交互：独立 loading/empty/error、重试、有效任务详情跳转和从详情返回后刷新。
- 架构审计：共享 shell、`ProductTabBar`、按钮和 route region owner 不回流到 route-private 实现。
- 几何验证：标准和最小支持视口内 `4 + 3` 行完整铺满正文，无大块空白、裁切、碰撞、TabBar 覆盖或首页纵向滚动。

### 10.2 视觉与微信验证

- 在实现前先基于已确认方向制作新的 `builds_home` canonical target。
- 目标 bounds 必须来自隔离的 target-only measurement；不得从现有 runtime、旧 CSS、概念稿或旧 redline 推导。
- 更新 `target-registry` 对应 route contract、target inventory/geometry、truth adaptation、component/asset contract 和核心交互合同。
- 候选实现完成后运行 target/runtime 结构与区域复核，再在真实微信 DevTools 验证职业选择、四个入口、最近任务详情跳转和满屏布局。
- 可视化概念稿、源码可编译和单元测试均不授予视觉 PASS；人工 acceptance 继续按 current UI control plane 记录。

## 11. 发布与恢复

本设计不改变后端、API 或数据 owner。实现候选可通过前端单路由移除最近任务 preview 并恢复上一版紧凑 `builds_home` composition，同时保留三个模拟器现有 `spec` 启动合同。若共享偏好代码已落地，恢复时可以停止读取，不需要迁移或删除用户业务数据。

## 12. 完成定义

只有以下条件同时成立，才能认为该首页优化完成：

1. 新 canonical target 和 route contracts 已更新且通过结构审计。
2. 四张紧凑卡、最近三次 SimC、满屏 `4 + 3` 布局、职业选择和启动专精解析满足第 9 节全部可见验收。
3. targeted tests、前端候选验证和必要的 Harness gate 通过。
4. 真实微信 DevTools 的首页视觉、职业选择、四入口、最近任务详情跳转和满屏布局得到用户明确验收。
5. 现有 canonical 数据、SimC 模板依赖和任务 owner 没有被首页展示便利性改写。
