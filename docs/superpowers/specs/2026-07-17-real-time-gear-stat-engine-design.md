## 1. 用户承诺与已确认边界

玩家在装备模拟中确认换上一件装备、调整宝石或附魔、或导入社区模板后，需要立即看到该组合的角色面板如何变化；这个面板要能和游戏内的**非战斗常态面板**逐项对照，而不是只看到装备词条的静态求和。

已由用户确认的口径：

- 包含等级、种族、职业/专精稳定被动、已确认装备、宝石、附魔、美化、稳定套装效果，以及属性换算规则。
- 不包含药水、饰品触发、战斗 Buff、临时 Proc 或其他条件效果；这些效果应独立标明条件，不能混入基础面板。
- 属性展示是独立、实时的确定性计算；SimulationCraft（下称 SimC）不能成为换装后属性更新的前置条件。

这不是“给静态装备总和补一个百分比”的展示修复。项目当前冰法和奥法案例中，页面的整数值分别能逐项还原为已选装备词条加已选强化的静态合计，但与英雄榜的主属性、耐力及副属性百分比明显不一致。静态合计必须继续保留为可追溯输入，不能伪装成最终角色面板。

## 2. 当前事实与问题定义

当前高频路径在 [装备架构](../../builds-architecture.md) 中定义为异步 `POST /api/websim/gear/stat-snapshots`：服务端生成 SimC profile，命中缓存时返回 immutable verified snapshot，未命中时入队等待 worker。前端在 `pages/builds/detail.js` 中只有拿到 `verified` snapshot 才展示换算值；否则回退为选中物品和强化的静态属性合计。

这条链路适合 SimC 结果的缓存、执行、诊断和复杂效果审计，但不满足用户的换装反馈：缓存未命中、worker 不可用、SimC 执行超时或 profile 不可执行时，玩家不应等待数秒至数十秒才看到一件装备从急速 100 变为 200 的影响。

当前事实不构成“现有项目的最终角色属性计算已正确”的证据：

- 冰法案例的页面属性 `智力 1,607 / 耐力 17,732 / 急速 1,343 / 精通 834 …` 与所选装备静态词条及强化精确相加；英雄榜为 `智力 2,485 / 耐力 23,001 / 急速 21% / 精通 54% …`。
- 奥法案例的页面属性 `智力 1,465 / 耐力 17,670 / 暴击 446 / 急速 880 / 精通 815 …` 同样与静态词条及强化精确相加；英雄榜为 `智力 2,462 / 耐力 22,938 / 暴击 19% / 急速 23% / 精通 37% / 全能 7%`。
- 这证明当前截图中的展示路径是“静态输入合计”，不能证明其为人物最终面板；也不能把原始 rating 与英雄榜百分比直接并列判断为换算误差。

两个英雄榜案例是首批候选对照，而不是立即可写死的黄金结论。角色可能已换装、页面抓取时点可能不同，且英雄榜可能有当前状态差异。升级为黄金样本前，必须固定角色链接、抓取时间、区域/服务器/角色、等级/种族/专精、天赋、完整装备实例与强化，以及每个待对照属性。

## 3. 反方质疑

### 3.1 “每次都跑 SimC 最准确”

不成立。SimC 对复杂战斗效果和 DPS 场景有价值，却不是基础角色面板的唯一权威来源；把它放进用户切装热路径会把 worker、缓存和执行时延暴露为交互等待，且无法解释为何一个简单换装不能立即反映基础属性。

### 3.2 “前端直接写一套公式最快”

不成立。游戏版本、等级换算、种族/专精和稳定被动变更后，前端硬编码会漂移；也会违反现有“客户端不自创装备来源或事实判断”的边界。

### 3.3 “先显示静态合计，后台回来再替换即可”

不成立。用户会把首屏数字理解为最终角色属性。静态合计可作为调试/来源明细，但不应占用“属性概览”的最终面板语义，也不能把旧的 verified 结果标作新配置的结果。

## 4. 方案比较与推荐

| 方案 | 说明 | 优点 | 不接受的风险 |
| --- | --- | --- | --- |
| A. 前端硬编码公式 | 小程序直接维护职业、等级和 rating 公式 | 最少网络等待 | 规则与版本漂移，无法证明来源或复测 |
| B. 每次切装调用同步后端计算 | 后端在每次变更后计算最终属性 | 后端单点权威 | 仍会受网络和服务时延影响，不能保证即时反馈 |
| C. 版本化规则包 + 本地确定性解释器 + 服务端参考复核 | 服务端发布可信计算上下文和规则版本；小程序本地执行同一规则语义；服务端参考实现和黄金样本复核 | 热路径即时、规则可追溯、可系统验证 | 需要维护显式的规则模型、版本和双端一致性测试 |

**推荐 C。** “同一计算器”在本合同中指同一份版本化规则、同一输入语义、同一运算顺序与同一 golden fixture；小程序解释器和服务端参考实现可以是不同语言，不能各自发明公式。

## 5. 目标架构与数据合同

```text
已确认的装备选择 / 社区模板导入
        │
        ├─ 服务端 Resolver：合法性、来源、物品实例与静态输入事实
        │
        └─ attributeCalculationContext（ruleRevision 固定）
                 │
                 ├─ 小程序确定性解释器 ──> 即时基础面板 + 本次变化
                 └─ 服务端参考解释器 ──> fixture、审计、保存/导入复核

SimC profile / worker ──> DPS、场景模拟、复杂条件效果、后台差异审计
```

### 5.1 服务端拥有的事实

服务端仍是装备与规则事实的唯一来源。每个可计算配置需要一个不可歧义的 `attributeCalculationContext`，至少包括：

- `manifestRevision`、`attributeRuleRevision`、游戏版本/规则生效范围。
- 职业、专精、种族、等级与只影响非战斗常态面板的稳定修正项。
- Resolver 已确认的每个槽位物品实例、物品等级/variant、宝石、附魔、美化、稳定套装条件及其静态属性事实。
- 绿色属性 rating 到结果百分比/效果的版本化转换：低档线性常数、递减曲线、乘算/加算修正、精度和舍入必须都能由规则数据表达；主属性、耐力、生命和法力等派生规则也必须有来源和版本。不得把递减曲线退化为一个只在单个样本成立的 `ratingPerPercent` 常数。
- 可追溯的规则引用。客户端不能用 itemId、名称、UI 文案或旧缓存自行推断缺失事实。

任一输入不完整、来源未验证、规则版本不支持或所选组合尚未 canonicalize 时，服务端返回结构化的“缺少何种事实/规则”问题，不返回伪造的最终值。

生产规则的来源、黄金样本与覆盖范围由 [属性规则来源账本](../../gear-attribute-rule-source-ledger.md) 管理。`fixture_only` 规则只可用于本地双端算术测试，不能随公开 `attributeCalculator` 发布；账本未完成时必须 fail-closed。

### 5.2 小程序热路径

页面在获得已解析的候选物品与规则上下文后，针对每一次**已确认**的装备、宝石、附魔或模板应用，在本地同步重算。一次重算必须：

1. 使用当前选择的完整 canonical input 和固定 `attributeRuleRevision`。
2. 先形成最终主属性、耐力及基础资源，再形成所有绿字原始 rating 和对应百分比/效果。
3. 同时产出当前值、与上一个已确认配置的差值、状态和可追溯的 rule revision。
4. 不请求 SimC、不等待 snapshot worker，也不把旧配置的结果当作新配置结果。

性能目标是：在输入事实和规则已在页面内时，从确认切装到属性状态更新的 p95 不高于 **100ms**；该目标需要在真实小程序设备/DevTools 性能证据中验证，而不是凭 JavaScript 单元测试声明完成。

如果用户选择了尚未解析的物品或缺少规则上下文，页面应显示“该装备的属性资料待补齐”，并请求轻量的 Resolver/规则数据；不得切回 SimC 等待，不得显示静态合计为最终属性，也不得把旧配置标为当前配置。此为数据可用性状态，不是属性计算中的正常异步状态。

### 5.3 展示合同

属性概览展示的每一项必须携带以下语义，而非只保存一个整数：

| 类别 | 必须展示/保留 | 示例 |
| --- | --- | --- |
| 主属性、耐力、生命、法力 | 最终数值、输入来源、规则版本 | `智力 2,485` |
| 暴击、急速、精通、全能 | 原始 rating 与结果百分比 | `急速 1,343（21.0%）` |
| 闪避、吸血、速度 | 原始 rating 与游戏定义的百分比或效果值 | `吸血 126（x.x%）` |
| 条件效果 | 不并入基础面板；展示触发条件和影响范围 | `饰品触发时另计` |

其中百分比、效果类型、精度和舍入都来自 `attributeRuleRevision`。如果某属性在当前游戏规则中没有可展示的百分比，必须明确显示其官方效果口径，而不能编造百分比。原始值仍保留，以便玩家检查装备词条和开发者排查误差。

### 5.4 与 SimC 的边界

现有 `gear_stat_snapshot` API、存储和 worker 不删除，也不再承担基础面板的用户热路径。它们保留用于：

- DPS/场景模拟与 SimC profile 的结果。
- 无法由非战斗确定性规则表达的条件效果说明。
- 后台抽样差异审计和黄金样本辅助验证。

任何 SimC 排队、失败、超时、worker 不可用或缓存未命中，只能影响对应的模拟/审计状态，不能阻塞或降级已具备完整规则输入的基础属性展示。

## 6. 范围与非目标

本需求的范围是装备模拟的非战斗常态面板及其导入/编辑一致性，不是重做整套 SimC、角色档案或社区推荐系统。

本期不做：

- 不承诺复刻战斗中所有触发、短时 Buff、药水、饰品 Proc 和战斗环境下的动态面板。
- 不把 SimC 的 DPS、战斗场景结论改写为属性面板结论。
- 不改变社区模板 observed-only 公开准入、装备合法性、Release/Manifest、天赋导入或现有 SimC 队列的事实边界。
- 不因页面缺少资料而由客户端猜测物品 variant、强化能力、职业被动或属性换算公式。

## 7. 验收与证据链

### 7.1 功能验收

- 同一职业/专精/种族/等级/天赋/装备/强化配置，无论由社区模板导入还是逐件换装形成，必须得到相同的 `attributeRuleRevision` 和逐字段属性结果。
- 已解析输入下，用户切装后的基础属性在本地即时刷新；断开 SimC worker 或制造 SimC 失败不得影响这条验证。
- 主属性、耐力、基础资源和全部绿字都不能只显示静态装备和；每个绿字保留 raw rating 与百分比/效果。
- 不完整或不可信输入不会显示“最终/已校验”属性；页面能说明缺少的装备事实或规则版本。
- 规则或游戏版本变化后，旧结果只能作为带 revision 的历史结果；不能静默沿用为新规则结果。

### 7.2 黄金样本

每个黄金样本至少保存：

```text
角色官方链接 + 抓取时间 + 区域/服务器/角色名
+ 等级/种族/职业/专精/天赋
+ 16 槽物品实例、variant/ilevel、宝石、附魔、美化
+ 英雄榜非战斗面板期望值 + 截图/原始响应证据
+ manifestRevision + attributeRuleRevision
```

冰法和奥法的现有对照先作为 `candidate`；身份、装备和时点可重复验证后，再提升为阻止回归的 fixture。黄金样本测试逐字段报告：输入差异、规则差异、原始 rating 差异和百分比/效果差异，不能只报告一个“对上/没对上”。

### 7.3 验证分层

- 本地：规则算术、舍入、非法输入、同配置双入口一致性、前端/后端 fixture parity、所有 green-stat 展示 contract。
- 真实运行：小程序中导入与手动切装截图、规则上下文缺失状态、SimC worker 不可用但基础面板仍即时可用、性能采样。
- 候选部署：最终候选 commit 的 `/api/websim/gear` 解析/规则 payload、Resolver 合法性、公共入口兼容、SimC 链路未回流、规则 revision 和页面 smoke。
- 上线后：记录黄金样本比对、规则发布版本、差异审计结果及 rollback 路径；不把历史 SimC snapshot 缓存命中率当作实时计算性能证据。

## 8. 影响图与 Owner 边界

| 分类 | 组件/合同 | 要求 |
| --- | --- | --- |
| 必须变更 | `server/websim_payload.py` 及其可抽取的 Resolver/属性规则边界 | 发布可信 `attributeCalculationContext`，保持服务端事实判断，不把规则归属下放给客户端 |
| 必须变更 | `pages/builds/detail.*`、装备 workbench 状态 | 以本地确定性结果渲染最终基础面板和差值；移除 SimC snapshot 对展示热路径的控制 |
| 必须变更 | 前后端测试、黄金样本 fixture、装备全链路 runbook | 固化 rule revision、双入口一致性、百分比/效果和性能证据 |
| 必须不变 | Resolver 合法性、observed-only 社区准入、Release/Manifest、强化容量和 canonical selection | 实时计算只能消费已确认事实，不能绕过或重写这些边界 |
| 必须不变 | `gear_stat_snapshot` 的 SimC 执行、队列、fencing 与健康语义 | 仍服务模拟/审计；不能被新展示路径伪装成失败或被删除 |
| 风险待查 | 游戏版本下各职业/种族/等级、稳定被动、套装、闪避/吸血/速度的准确规则来源 | 未被证据化前不得进入 `attributeRuleRevision` 或被前端猜测 |
| 需要证据 | 英雄榜样本与社区模板是否为同一角色同一时点同一装备实例 | 未确认前只能是候选样本，不能以截图覆盖 Resolver 事实 |

后端 `websim_payload` 属于现有热点，页面 `detail` 是高频用户路径；实施前必须先补足当前快照回退、canonical selection 和 `setData` 状态的特征测试。新计算规则应建立清晰的纯函数/数据边界，不能在路由或页面事件中散落公式。

## 9. 风险、降级与回滚

| 风险 | 防护/降级 |
| --- | --- |
| 规则不完整或游戏版本更新 | 用 `attributeRuleRevision` fail-closed；展示明确资料缺口，发布新规则前跑黄金样本 |
| 客户端与服务端解释器漂移 | 使用同一规则模型、固定运算顺序、跨端 fixture parity；差异阻止规则发布 |
| 物品实例或强化来源不完整 | 只由 Resolver 补齐；不显示伪造最终面板 |
| 条件效果被误加到常态面板 | 规则分类为 stable/conditional；conditional 只单列说明 |
| 新展示回归或线上样本异常 | `feature_hide` 隐藏实时面板入口并恢复上一个已验证版本；`code_rollback` 回退客户端/服务端规则解析；规则数据无写入型污染时不需要数据恢复 |
| SimC 链路被意外耦合回展示 | 候选 smoke 明确模拟 worker 停止/失败时基础面板仍可用；失败则不允许发布 |

## 10. 用户已拍板的事项与后续门槛

已拍板：采用“非战斗常态面板”口径，采用方案 C，基础属性展示与 SimC 解耦。

进入实现前仍必须完成：

1. 实施计划：拆分规则模型、服务端参考解释器、规则上下文、前端解释器/UI、fixture 和候选发布验证，且不把该计划写成 SimC 重构。
2. 规则来源审计：逐项确认第一批职业/专精/种族/等级与八类绿字的可验证来源及缺口。
3. 黄金样本建档：先确认冰法与奥法案例的同一时点输入，再将它们纳入回归。
4. 实施前工程健康基线：特征测试覆盖当前静态回退与异步 snapshot 行为，防止无意破坏模拟任务。

在上述实施计划被确认前，本合同只允许设计、调查和 fixture 准备；不允许声称已修复属性计算，也不允许改变任何运行时接口或展示行为。
