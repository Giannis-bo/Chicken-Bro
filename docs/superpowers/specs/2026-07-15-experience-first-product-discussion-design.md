# 用户体验优先讨论协议设计

**状态：** 已获用户确认，2026-07-15。

## 目标

让后续功能、Bug 与需求讨论优先帮助团队理解用户正在完成的任务、当前摩擦和可感知的成功，而不是从实现细节反推产品价值。技术可行性和可信边界仍需保留，但默认作为支撑体验决策的第二层。

## 备选方式与决定

1. **仅作为沟通提醒。** 成本最低，但容易在紧急排查或实现讨论中被忽略，无法形成稳定的跨 agent 约束。
2. **项目级默认讨论门禁（采用）。** 把固定输出顺序、Bug 表达、事实/假设区分和双重验收写入 `AGENTS.md` 与 Harness；用户可明确要求切换到技术方案/实施视角。
3. **独立 UX 评审流程。** 能提供更深的设计审查，但会把每个小问题都变成正式设计项目，不符合仓库的 Light/Standard/Strict 分层。

## 协议

### 适用范围

适用于所有功能、Bug 和需求讨论，包括先行的只读诊断。只读排查不需要等待产品讨论，但任何建议的修复、方案或完成声明必须回到用户体验表述。

### 默认叙述顺序

1. 用户、场景与要完成的任务。
2. 当前用户旅程中的摩擦、伤害或信任风险。
3. 目标体验：主路径、空态、失败态、证据不足和恢复路径。
4. 用户可观察的完成信号与验收条件。
5. 事实、产品假设和技术假设的边界。
6. 技术选项、约束、风险、影响面与实施计划。

Bug 额外要求先说明“用户看到什么、造成什么影响、恢复后应如何表现”，再讨论根因、接口、文件或代码改动。

### 技术层的边界

本协议不要求隐藏技术事实。数据真实度、隐私、性能、可用性、降级、回滚和证据等级会影响用户承诺时，必须明确说明。用户明确要求技术设计、排障或实施时，技术层可以成为主叙述，但仍需保留用户影响与验收。

### 诚实性与验收

内部 evidence、实现便利、未验证数据和临时 fallback 不能被包装为用户已获得的能力。体验交付的最低条件是：用户侧验收标准明确，且 Harness 要求的测试、运行/线上证据和回滚边界与之相符；任意一项不足都只能标为待验证、降级或阻断。

## 落点与非目标

- `AGENTS.md`：所有 agent 的持久化入口规则。
- `docs/harness.md`：Light/Standard/Strict 共用的可执行讨论门禁。
- `docs/roadmap.md`：记录该协作规则已采纳及其当前证据入口。

不新增运行时代码、自动化 UX 评分、额外审批层或独立设计评审流程；既有 Harness 分级和发布验证强度不变。

## 验收

- 新的功能、Bug 和需求回复可先定位用户任务、摩擦、目标体验与用户侧完成信号。
- Bug 的建议不再以文件/接口为开头；技术分析仍能完整解释体验、可信边界或可行性受限的原因。
- 任何进入实现的需求同时写明用户侧验收与适用的 Harness 证据/回滚要求。
