## 已确认的设计问题

`_client_events`关闭时调用events.close；ChatApplication捕获GeneratorExit执行_cancel_run，将状态写failed、错误写CODEX_EXECUTION_FAILED，并关闭Codex生成器。因此连接生命周期与生成任务耦合，且连接中断与真正执行异常使用同一码。

现有测试三项fresh通过：started后关闭、delta中关闭均failed；completed后关闭保留succeeded。单独内存实验也得到assistant_message_id=None、CODEX_EXECUTION_FAILED及codexClosed=true，不需要模型崩溃即可产生该错误。

## 用户确认后的本地修复与验证

HTTP 改为订阅服务端后台生成，关闭连接只脱离订阅；生成仍通过原 ChatApplication 写入终态与回答。每个应用进程最多 8 个交付任务；每订阅最多缓存 64 个后续事件且估算容量不超过 256 KiB，慢订阅被断开后生产者继续保存结果。沿用 480 秒模型超时、账号数据库互斥、幂等与 owner 隔离。日志增加 run 关联的订阅关闭、超时/协议异常、应用异常及模型非零退出分类，不记录原始 stderr 或用户输入。

这不是持久化任务队列：进程终止不自动续跑。遗留 streaming 在任务年龄超过 480+60 秒且触发既有恢复入口后标记失败，需用户重试；不会自动重放可能有副作用的工具。重新进入会话可读取已保存结果，不承诺当前客户端自动订阅原流或即时轮询更新。

验证：435 项后端测试通过（含 7 项新交付测试与 ASGI http.disconnect）；62 项控制面测试通过；独立临时 PostgreSQL 的 9 项进度/账号约束测试通过，覆盖断线后真实数据库保存、重建应用后 Web 读取、另一 owner 拒绝、重复请求不再调用模型及账号互斥。临时数据库已停止。详见 backend-tests.log、control-tests.log、postgres-tests.log。
