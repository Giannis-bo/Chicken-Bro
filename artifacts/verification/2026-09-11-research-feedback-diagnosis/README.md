## 已确认根因

### 1. 证据已取得，但下一轮没有取用通道

14:38:24、14:38:27、14:38:30 的成功工具结果已分别返回三人的 `combatantInfo.stats`、18 槽装备和天赋信息。15:18:49 又成功读取用户自己的同场属性。已有日志属性如下（WCL 原始数值，副属性为等级，不是百分比）：

参考者 A 相比用户暴击等级多 246、急速等级少 206。这足以回答是否存在配装属性差异，但不能直接推导技能暴击率差异全部由装备造成。

`ChatApplication._prompt` 只传最近 20 条用户/助手消息，每条截取 4000 字符；不会恢复 `chat.tool_results`。原生每轮新建 ephemeral thread。`WclRunReader` 缓存只存于本轮 Worker 对象，60 秒过期。结果虽保存了，模型下一轮却看不到可检索的历史证据。

最后被拒绝的请求中，有两条 request_hash 分别与先前成功的 overview 请求完全相同。正常读取已有证据不应要求用户再次提供截图或消耗新研究额度。

### 2. 治疗汇总能力与模型使用方式不匹配

当前 overview GraphQL 只读取 playerDetails、casts、damage，没有治疗汇总表。`validate_wcl_options` 明确禁止 overview 带 dataType，因此模型尝试 `view=overview,dataType=Healing` 会在本地失败。

用有限的 URL 参数排列重建请求，按 ToolRecorder 的原 SHA256 算法与生产 request_hash 精确匹配，确认 18 条失败中的 14 条是上述组合。这里只匹配已知候选，不声称恢复了其余 4 条失败的参数或原因。

这些已匹配调用不会到达 WCL 上游，不应称为 WCL 接口故障。URL 中的 `type=healing` 或 `options=8` 也不自动使目前的 GraphQL 查询具备治疗汇总能力。

### 3. 参数错误先扣额度，错误原因又被隐藏

`ChickenbroSourceGateway.query` 在执行来源参数校验前调用 budget.reserve。已在本地复现：overview + Healing 先增加 calls=1，再抛出 InvalidSourceLink。

WorkerToolServer 将异常统一返回 CHAT_TOOL_UNAVAILABLE，ToolRecorder 的 failed 记录不保存结构化失败分类。模型看不到“本地参数不支持”的明确原因，因而跨轮、换 URL 反复尝试。14 条确定的本地错误中，8 条发生在持久研究建立之后，实际侵占其 48 次预算。

### 4. 累计工作次数成为业务追问的永久禁令

48 次硬上限不区分扩大样本、对原有三人补查、读取已有结果、纠正内部错误。即使玩家数、战斗数都很小，也会让正常研究锁死。玩家跨来源身份合并还漏掉普通 report actor 与角色链接的对应，但这次没有触发玩家数上限，不是直接阻断原因。

1. **先让已有证据可复用。** 按 owner/conversation 和报告、战斗、角色、视图、窗口建立有界证据索引；向模型提供紧凑目录，按缺口取必要字段。历史数据只作有来源的证据，不作指令；支持本次建立持久研究前的同对话结果，不跨用户读取。不要把数 MB 工具原文全塞回上下文。
2. **补齐治疗汇总工具。** 直接返回整场/指定窗口的有效、过量、吸收、技能构成、次数和暴击统计及其覆盖口径；先取汇总再定位需要的施法/增益/承伤窗口。不得以样本事件小计代替完整总量，也不能根据技能次数直接认定玩家操作错误。具体 GraphQL 字段与口径须用官方合同和有限真实样本验证。
3. **把校验与计费移到正确位置。** 本地无效参数在预留上游研究额度之前拒绝；提供可纠正的结构化错误。无效尝试仍受本轮工具次数/时间保护，不能无限重试。真实上游失败保留实际成本记录并有限重试；缓存/历史读取不重复计算上游消耗。
4. **区分研究范围与执行保护。** 先识别目标与工作量，防止跨轮扩大为 Top100 或穷举；原有限对象内的合理追问走证据复用和受控补证。工作次数用于停止无进展循环和规划下一步，不能直接成为整个研究永久拒答的理由。不能仅由模型一句“合理”无限提高预算；续查依据必须包含固定对象、具体缺口、预期信息增益和可审计的有界执行。这里没有假定新的固定数值上限。
